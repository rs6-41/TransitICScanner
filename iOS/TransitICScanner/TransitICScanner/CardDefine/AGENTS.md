# カード定義実装ルール

このファイルは `iOS/TransitICScanner/TransitICScanner/CardDefine/` 以下でカード定義または読取実装を追加・変更する作業に適用する。カード仕様書から実装を追加するときは、以下をすべて守ること。

## 1. 仕様の根拠

- 作業前に対象の `doc/cards/<カードID>.md` を最初から最後まで読み、関連する開発文書も確認する。特に `doc/dev/README.md`、`doc/dev/sortName.md`、必要に応じて `doc/dev/PLAN.md` を参照する。
- 仕様書にないサービスコード、ブロック形式、バイト順、取引種別、日付規則、残高計算、読取順序、上限値を推測して実装してはならない。
- 曖昧な記述、相互に矛盾する表、未定義値、必要なサンプルデータの欠落があれば、影響する実装を保留し、根拠箇所と未確定事項を報告する。値を仮置きしたり、近似カードの仕様を流用したりしない。
- 仕様書と既存コードが異なる場合は、既存実装に合わせて仕様を黙って変更しない。仕様の記述とコードの挙動を照合し、正しい解釈が確定できない箇所を明示する。
- 実カードの識別子、IDm、取引履歴などをサンプルとして追加する場合は、仕様書またはリポジトリ内で明示的にサンプルと確認できる値だけを使う。実利用者のデータを捏造・流用しない。

## 2. 既存アーキテクチャとの整合

- 新規カードの実装前に `CardModel.swift`、`ScannerBranch.swift`、`Area.swift`、`cardDesignList.swift`、`prefSort.swift` と、仕様が近い既存カードの定義・読取処理・Converterを読む。近いカードのコードは構造の参考に限り、カード固有の仕様値や変換規則をコピーしない。
- カード情報は `CardInfo` と `ScanOption` の既存モデルで表現する。共通モデルや既存の型を確認せずに重複モデルを追加しない。
- カードの識別名、`ScanOption.name`、ConverterType、switch分岐、一覧への掲載状態は相互に一致させる。新規実装では、必要な `ScannerBranch.swift` の `devCards` / `featureCards` / `relCards` のいずれかへの登録、`switchCard(name:)` の分岐、`ConverterType` のcaseおよび表示変換分岐を確認し、対象カードの公開状態に応じて漏れなく更新する。仕様または依頼から状態を確定できない場合は、リリース済み一覧へ追加せず、確認事項として報告する。
- ロゴ名、Asset Catalog名、カード名・短縮名・説明・ソート名のローカライズキー、検索語、地域・国・都道府県、通貨、読取方式、履歴件数、FeliCa system code等は、仕様と既存データの両方で根拠を確認して設定する。根拠がなければ創作しない。
- Converterは既存の `DisplayHistory` / `DisplayCardInfo` の契約に合わせ、未知の取引種別を既存の汎用表示に落とす。未定義値を既知の取引として誤表示しない。
- 読取失敗、非対応タグ、データ長不正、空データ、無効な履歴、日付範囲外、件数境界を明示的に扱う。配列添字や整数変換は検証後に行い、入力データの不正でクラッシュさせない。
- CoreNFCのコールバック/API利用は既存の非同期・セッション管理のパターンに合わせる。継続処理は成功・失敗のすべての経路で一度だけ完了し、失敗時にセッションやTaskを不整合な状態にしない。
- サンプル結果は実装した仕様を表す値にする。仕様書に完全なサンプルがない場合、任意の生データや駅コードを実測値のように作らず、サンプルを省略できるか既存設計を確認し、できなければ不足として報告する。

## 3. 変更範囲と登録

- 変更前に既存の作業ツリー差分を確認し、ユーザーの変更を上書き・巻き戻ししない。
- 追加ファイルは既存カードと同じ命名・ディレクトリ構成を基本とする（例：`<cardID>/<cardID>.swift`、`<cardID>/<cardID>Converter.swift`）。一つの共有実装を使う複数カードでは、既存の共有カード定義パターンを確認してから適用する。
- `ScannerBranch.swift` だけでなく、ローカライズ文字列（各言語の `.xcstrings` 等）、カードロゴのAsset Catalog、カードデザイン一覧など参照される登録箇所を検索し、追加が必要なものをすべて反映する。存在しない画像や未確認のファイル名を登録しない。
- Xcode projectがファイルを明示登録する方式かどうかを `project.pbxproj` で確認する。必要な方式の場合だけ、追加ファイルをBuild Phases / File Referencesへ登録する。
- 無関係なリファクタ、他カードの挙動変更、ドキュメントの仕様変更を混ぜない。カード仕様の修正自体が必要なら、その変更を分けて根拠を記録する。

## 4. 完了前の確認

- 実装と仕様書を項目ごとに照合する。System Code、Service Code、読取件数、ブロック指定、バイト位置、バイト順、マスク・シフト、日時、残高、取引分類、履歴順をチェックリストとして確認する。
- 新規カードなら、一覧登録、スキャン分岐、Converterの全case、カード名・説明・検索・ソート用ローカライズ、Asset参照、サンプルを個別に確認する。適用対象外の項目は理由を明示する。
- 不正・境界入力について、既存テスト基盤と対象コードのテスト方法を調べる。テスト基盤がある場合は、バイト列デコード、未知の取引種別、空・不正データ、件数上限を含む必要なテストを追加する。テストを追加・実行できない場合は、その理由を報告し、成功したように記載しない。
- ビルドまたは静的確認を実行する場合、対象と結果を正確に記録する。実機カードでの読取を検証していない場合、実機確認済みと表現しない。
- 最終報告では変更ファイル、仕様との照合結果、実施した確認、未解決の仕様上の不確実性を簡潔に示す。

## 5. 禁止事項

- 仕様書にないデータの意味を断定すること。
- 読めなかったブロックを正常なゼロ残高・空履歴と見なすこと。
- 未知の取引コードを既知の運賃・チャージ等として表示すること。
- 出典のないダミー値を、本物のカード仕様や実測サンプルとして登録すること。
- 失敗を `try?` 等で握りつぶし、正常値として続行すること。
- カード追加の一部だけを行い、一覧・読取分岐・Converter・必要な表示資源の整合確認を省略すること。
