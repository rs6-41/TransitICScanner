# 調査・iOS実装・リポジトリ整備Issue

## 入力と重複確認

Git remoteで対象リポジトリを確認する。カードの正式名、略称、旧ID、地域、世代で既存Issueを検索し、open/closedの両方を見る。名称一致だけで別世代のカードをまとめない。既存Issueがあれば不足部分を追記するか新規に分けるかを依頼の目的で決め、完了済みIssueを勝手に再開しない。

README・AGENTS.md・スキル等の整備では、カード名でなく目的・対象ファイル・既存の関連作業で検索する。[整備Issueテンプレート](../assets/repository-issue.md)を使い、タイトルは `【開発】<整備内容>` とする。カードID・カード世代を捏造せず、調査とiOS実装の2件へ機械的に分割しない。

「調査とiOS実装のIssue」と指定されたら、調査と実装を別Issueにする。片方だけの指定なら片方だけ作る。実際のカード・対象が不明ならテンプレートの下書きまでは作り、対象を特定してから投稿する。

## タイトル・本文・メタデータ

- 調査: `【調査】<カード名>（<地域>）`。本文は [調査Issueテンプレート](../assets/research-issue.md) を使う。
- iOS: `【iOS】<カード名>実装`。本文は [iOS Issueテンプレート](../assets/ios-issue.md) を使う。
- すべての作業チェックは未完了から開始し、既存資料で完了が確かめられる項目だけ、その証拠を添えて更新する。
- 本文に正規cardID、仕様書パス、対象世代、根拠資料、未確定事項を記載する。cardIDが未確定ならそのまま明記し、名前から勝手に採番しない。
- 現在存在するラベルを検索・確認して選ぶ。過去例には `Investigation (調査)`、`iOS / macOS` と地域ラベルがあるが、固定で新設・流用しない。マイルストーン・Assigneeはユーザー指定または確認済みの対象だけを使う。
- Codexが作成した場合は本文にOpenAI Codexによる作業と明記する。組織名・GitHub App名をAssigneeユーザーと仮定しない。

## Agentラベルの必須付与

LLMが作成・更新・コメント・状態変更等を書き込むIssue・PRには、種類や作業者アカウントによらず `Agent` を必ず付ける。具体的な操作は次のとおり。

1. 新規Issueは作成APIの `labels` に `Agent` と必要な既存ラベルを指定する。
2. 既存Issueは加算式のラベル操作で `Agent` を追加し、既存ラベルを維持する。既に付いていれば重ねて追加する必要はない。
3. PRまで依頼された場合は指定されたbase/headで作成し、作成APIにラベル指定がなければ直後に加算する。GitHubではPRもIssueのラベルAPIを使える。
4. 返却値または再取得で、本文だけでなくlabelsに `Agent` があることを確認する。付与に失敗したら投稿済みURLと未完了操作を報告し、完了・付与済みと記載しない。再投稿や無関係なIssueへの一括付与はしない。

下書きだけの場合は投稿メタデータに `labels: [Agent]` を記載する。ラベルを設定したようには報告しない。閲覧・検索のみで他のIssueへラベルを付けない。

## 投稿と相互リンク

作成前に実際に投稿する本文を完成させ、テンプレート変数を埋める。両Issueを作る場合は、調査IssueのURLを実装Issueに入れ、実装Issue作成後に調査IssueにもURLを追記する。Issue番号を推測しない。

GitHubの返却URL・タイトル・本文を確認し、作成したIssueと既存Issueへの追記を区別して報告する。作成エラー時に同じIssueを無制限に再投稿しない。
